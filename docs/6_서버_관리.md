# 서버 관리 (관리자 전용)

공용 계정 하나(`shareduser`)로 여럿이 쓰는 B200 서버를 root 계정으로 관리하는 방법이에요. 팀원에게 보여 줄 규칙은 `team/` 에 따로 있어요.

방향은 두 가지예요.

- **팀원에게 새 명령을 외우게 하지 않아요.** 팀원은 `docker`, `nvidia-smi`, FileZilla를 평소처럼 쓰고, 도우미가 그 뒤에서 이름표를 붙이고 경고해요.
- **막기보다 알려요.** 멈추거나 지우는 것은 관리자가 판단해요. 알림도 같은 내용은 하루나 한 주에 한 번만 보내요.

### 왜 공용 계정의 sudo·docker 그룹을 확인하나요

공용 계정에 sudo 나 docker 그룹이 있으면 팀원 누구든 root 가 될 수 있어요. 그러면 위의 잠금이 모두 의미가 없어져요. 지금은 둘 다 없어요. 다만 서버 관리 팀이 나중에 넣을 수도 있어서, `admin_setup.sh` 를 실행할 때마다 **확인만** 하고 있으면 `[주의]` 로 알려 줘요(바꾸지는 않아요).

### 왜 `/app` 을 잠그나요

root 로 도는 스크립트(설치, 관리자 설정, 정기 점검)는 **공용 계정이 쓸 수 있는 곳에 파일을 만들거나 권한을 바꾸지 않아요.** `chown`·`chmod` 와 파일 쓰기는 링크를 따라가서, 공용 계정이 `/app/shared` 나 기록 파일 자리에 `/etc` 로 가는 링크를 미리 심어 두면 root 가 시스템 파일의 주인이나 내용을 바꾸게 돼요(이 저장소에서 실제로 재현했어요).

| 곳 | 주인 | 누가 써요 |
|---|---|---|
| `/app`, `/app/shared`, `/app/inbox`, `/app/state` | root | root |
| `/app/state/reports`, `gpu_log`, `notice` | root | 정기 점검(root) |
| `/app/workspace`, `/app/state/history`, `images`, `notice_seen` | 공용 계정 | 팀원, docker 도우미 |

`admin_setup.sh` 는 실행할 때마다 이 주인을 다시 맞추고, 위 폴더 중 링크가 있으면 멈춰요.
정기 점검(root)은 도커 이름표, 프로세스 환경의 이름, NAS의 점검 파일처럼 **누구나 정할 수 있는 값**을 읽어요. 이런 값은 이름·숫자 모양이 맞을 때만 쓰고, 계산식이나 파일 경로에 그대로 넣지 않아요.

### 왜 `/app/inbox` 를 잠그나요

관리자는 `/app/inbox` 의 스크립트를 root 로 실행해요. 이 폴더를 공용 계정이 고칠 수 있으면, 누구든 스크립트에 한 줄을 넣어 root 로 실행시킬 수 있어요. 그래서 설치 파일은 **root 계정의 FileZilla로** 올려요.
root 로 FileZilla 접속이 안 되면, 공용 계정으로 `/app/workspace` 에 올린 뒤 root 로 `/app/inbox` 에 복사하고, **복사한 파일**의 지문이 접근 PC의 값과 같은지 확인한 뒤 실행하세요.
묶음 안의 `MANIFEST.sha256` 은 같이 바뀔 수 있어서 이 확인에는 못 써요.

```powershell
# [접근 PC] PowerShell
Get-FileHash pack\b200-pack.tar          # 데이터셋·모델은 datasets\MANIFEST.sha256, datasets\datasets_install.sh 처럼 두 파일
```

```bash
# [B200 서버] root
cp /app/workspace/<올린 곳>/b200-pack.tar /app/inbox/ && sha256sum /app/inbox/b200-pack.tar
```

## 처음 설정 순서

`docs/5_우분투_재설치.md` 의 순서를 따르세요. 서버 2대 모두 같은 순서로 해요.

1. `check_server.sh`, `check_network.sh` 로 서버 점검
2. root 로 `admin_setup.sh`(맨 먼저: `/app` 잠금) → `/app/shared/team.txt` 에 팀원을 적고 한 번 더 실행
3. root 로 `pack_install.sh /app/shared`
4. root 로 `docker_install.sh`
5. root 로 `datasets_install.sh`, `models_install.sh`
6. 공용 계정으로 접속해 이름 목록이 나오는지, `nvidia-smi` 아래 "누가 쓰나" 표가 나오는지, `b200 doctor <PyTorch 이미지>` 가 정상인지 확인

## 팀원과 GPU 배분 바꾸기

| 할 일 | 서버 (root) | 엑셀 (`team/서버_사용_규칙.xlsx`) |
|---|---|---|
| 팀원 추가 | `/app/shared/team.txt` 에 `이름 그룹` 한 줄 → `bash admin_setup.sh`(작업 폴더 생성) | '팀원' 시트에 같은 내용 |
| 팀원 삭제 | `team.txt` 에서 줄 삭제. 작업 폴더는 NAS로 옮긴 뒤 지워요 | '팀원' 시트에서 삭제 |
| GPU 배분 변경 | `/app/shared/gpu_alloc.txt` 수정 | 'GPU 배분' 시트 수정 |

- 접속할 때 목록의 번호는 `team.txt` 에 적은 순서예요.

- 그룹 이름은 `gpu_alloc.txt` 의 그룹 이름과 글자까지 같아야 해요.
- 서버가 2대면 `gpu_alloc.txt` 도 서버마다 따로예요.

## 알림

10분마다 GPU와 디스크를 보고, 아래 경우에만 알려요. 멈추거나 지우지는 않아요.

| 알림 | 받는 사람 | 기준(`/app/shared/b200.conf`) | 얼마나 자주 |
|---|---|---|---|
| 한 GPU를 두 사람 이상이 씀 | 그 사람들 | | 하루 한 번 |
| GPU를 잡고 사용률 0% | 그 사람 | `IDLE_HOURS=12` | 하루 한 번 |
| 디스크가 참 | 작업 폴더가 큰 3명, 관리자 | `DISK_ALERT=85` | 주 한 번 |
| 오래 안 쓴 도커 이미지 | 들여온 사람(모르면 관리자) | `IMAGE_NOTICE_DAYS=30` | 주 한 번 |
| 이름 없는 GPU 작업 | 관리자 | | 하루 한 번 |
| GPU 오류(ECC, Xid) | 관리자 | | 하루 한 번 |
| 주간 보고서 | 관리자 | | 주 한 번 |

- 팀원은 열어 둔 창에 한 줄로 받고, 다음에 접속할 때도 봐요. 관리자는 root 로 접속할 때 봐요.
- 알림 기록: `/app/state/notice/<이름>.txt`. 주간 보고서: `/app/state/reports/<날짜>.txt`.
- `docker run` 때의 경고 기준 `MAX_GPUS=4` 도 같은 파일에 있어요. 숫자를 바꾸면 `team/` 문서의 숫자도 같이 바꿔요.

### GPU 사용 기록은 왜 남기나요

공용 계정이라 `nvidia-smi` 만으로는 누가 GPU를 쓰는지 알 수 없어요. 10분마다 "GPU, 이름, 컨테이너, 사용률"을 `/app/state/gpu_log/<월>.tsv` 에 적어 두면 세 가지를 할 수 있어요.

- GPU를 잡고 놀고 있는지 알 수 있어요. 한 번 볼 때 0%인 것은 흔하니까, 12시간 내내 0%인지는 기록이 있어야 판단할 수 있어요.
- 그룹별 배분이 실제 사용량과 맞는지 주간 보고서로 볼 수 있어요. 배분을 바꿀 근거가 돼요.
- 다툼이 생기면 언제 누가 썼는지 확인할 수 있어요.

### 사람 구분은 어떻게 하나요

| GPU 프로세스가 | 누구로 보나 |
|---|---|
| 컨테이너 안에 있음 | 그 컨테이너의 이름표(`b200.USER`). 이름표가 없으면 컨테이너 이름만 보여요 |
| 서버에서 직접 실행 | 프로세스 환경의 `B200_USER`(접속할 때 고른 이름이 따라가요) |
| 둘 다 아님 | 작업 폴더(`/app/workspace/<이름>`) 안에서 실행했으면 그 이름, 아니면 "이름 없음" |

이름은 본인이 고르는 것이라 남의 이름을 고를 수도 있어요. 팀 안의 약속으로 충분하다고 보고, 따로 막지 않아요.

### HIWARE 기록은요?

HIWARE는 접속 기록과 세션 녹화를 HIWARE 관리 화면에 남겨요. 보통 보안 담당이 관리하고, 서버 관리자가 직접 보지는 못해요. 그래서 평소에는 쓰지 않아요. 심각한 일이 생겼을 때만 보안 담당에게 시간과 계정(`shareduser`)을 알려 주고 확인을 요청하세요.
서버 안에서는 이름별 명령 기록(`/app/state/history/<이름>.bash_history`)이 남지만, 공용 계정이 고칠 수 있는 파일이라 참고용이에요.

## 두 서버와 NAS

두 서버가 서로 연결돼 있는지, 대역폭이 얼마인지, NAS 속도가 얼마인지는 `check_network.sh` 로 재요. 설정은 아무것도 바꾸지 않아요.

### 한 번에 재기 (턴키)

두 서버에서 각각 아래 한 줄만 실행하세요. 두 번째 서버는 10분 안에만 실행하면 돼요.

```bash
# [서버 1, 서버 2 각각] root
cd /app/inbox && bash check_network.sh all
```

| 하는 일 | 내용 |
|---|---|
| 짝 찾기 | 같은 NAS(`/data/tmp/.b200_net`)에 서로의 주소를 적어 두고 짝을 찾아요. IP를 적지 않아도 돼요 |
| 서버 사이 이더넷 | 양쪽이 동시에 보내고 받아요 |
| 서버 사이 InfiniBand(IPoIB) | 두 서버 모두 InfiniBand IP가 있으면 재요 |
| 서버 사이 RDMA | 같은 이름의 카드끼리(`mlx5_0`↔`mlx5_0` …) `ib_write_bw` 로 재요. 두 서버를 묶어 학습할 수 있는지 여기서 갈려요(400 Gbps 에 가까워야 정상) |
| 로컬 SSD, NAS | 1줄기와 8줄기. NAS 는 두 서버가 차례로 재요(동시에 재면 값이 반이 돼요) |
| InfiniBand 망 | 카드마다 어떤 서버·장비가 보이는지(`ibhosts`, root). 짝 서버가 보이면 같은 망이에요 |
| 보고서 | 실행한 폴더에 `network_report_<서버>_<시각>.txt`. 두 파일을 README 에 붙여요 |

- RDMA 는 양쪽에 `perftest`, 망 조회는 `infiniband-diags` 가 있어야 해요. 없으면 `[주의]` 를 남기고 나머지만 재요. 보통 InfiniBand 드라이버(DOCA·MLNX OFED)와 함께 깔려 있어요.
- 짝을 10분 안에 못 찾으면 그 서버만 재요. NAS 를 못 찾으면 `bash check_network.sh all <NAS 안 쓸 수 있는 폴더>` 로 적어 줘요.
- 쓰는 포트: 5201·5202(TCP), 18515~18520(RDMA 준비). 서버 사이 방화벽이 막으면 양쪽 모두 `PORT=다른번호` 를 앞에 붙여요.

### 하나씩 재기

```bash
# [서버 A, B 각각] 네트워크 카드 종류·속도, NAS 연결 경로, 다른 서버까지 연결
bash /app/inbox/check_network.sh <다른 서버 IP>

# [서버 B] 받는 쪽을 먼저 켜요(2분 기다려요)
bash /app/inbox/check_network.sh listen
# [서버 A] 보내는 쪽(10초)
bash /app/inbox/check_network.sh send <서버 B IP>

# [각 서버] NAS 와 로컬 SSD 의 쓰기·읽기 속도(시험 파일 4 GB를 쓰고 지워요)
bash /app/inbox/check_network.sh disk <NAS 안에 쓸 수 있는 폴더>
bash /app/inbox/check_network.sh disk /app/workspace
```

| 결과에서 볼 것 | 뜻 |
|---|---|
| 네트워크 카드의 속도 | 이론상 최대치예요. 100 Gbps 카드 ≈ 12.5 GB/s |
| InfiniBand·RoCE 항목이 `ACTIVE` | GPU 서버끼리 빠르게 주고받는 카드가 연결돼 있어요. 어디에 연결됐는지는 서버 관리 팀에 물어보세요 |
| "다른 서버"의 응답, SSH(22) | 두 서버가 직접 이어져 있는지 |
| `send`·`listen` 결과 | 실제 서버 사이 속도. `iperf3` 가 있으면 그것으로, 없으면 python 으로 재요(100 Gbps 이상에서는 낮게 나올 수 있어요) |
| `disk` 결과 | NAS 가 로컬 SSD보다 많이 느리면, 학습 데이터는 `/app` 에 두고 NAS 는 보관용으로 써요 |

두 서버가 연결돼 있지 않으면, 데이터셋·모델은 서버마다 접근 PC에서 따로 올리거나 NAS를 거쳐 옮겨요. 서버 사이 방화벽(포트 5201)이 막혀 있으면 `PORT=다른번호` 를 앞에 붙여 다시 재요.

### 측정 결과 (2026-10-28, server1 → server2)

원본 기록은 README 끝의 "네트워크 점검 결과"에 있어요.

| 구간 | 연결 | 잰 값 | 판단 |
|---|---|---|---|
| 서버 ↔ 서버 | `bond0` = 10 Gbps 이더넷 2장, 왕복 0.057 ms | 8줄기 **2.28 GB/s (18.3 Gbps)** | 20 Gbps 의 92%라 회선이 꽉 찬 값이에요. 같은 스위치에 붙어 있어요 |
| 서버 → NAS | InfiniBand 400 Gbps(`ib`), NFSv3 over RDMA, `nconnect=24` | 1줄기 쓰기 **1.82 GB/s**, 읽기 **4.3 GB/s** | 서버 사이 이더넷보다 읽기가 약 2배 빨라요. 여러 줄기면 더 나올 수 있어요 |
| InfiniBand | NDR 400 Gbps 6포트 모두 `ACTIVE`. 2포트만 IP(NAS망-IP·22, NAS 망) | 아직 안 잼 | IP 없는 4포트는 GPU 서버끼리 RDMA(NCCL) 용일 가능성이 커요 |

NAS(`NAS망-IP:/nas`)는 경로 모양으로 보아 Dell PowerScale(Isilon)이에요.

**정한 것**

- **서버 사이로 큰 파일을 옮길 때는 NAS를 거쳐요.** 두 서버가 같은 NAS를 쓰니 옮길 필요 없이 한쪽이 쓰고 다른 쪽이 읽으면 돼요. 이더넷(2.3 GB/s, 한 연결은 1.2 GB/s 안팎)보다 빨라요.
- **데이터셋·모델 반입은 서버 한 대에만 올려요.** 접근 PC → 서버 1의 `/app/inbox` → 설치한 뒤 NAS에 복사 → 서버 2는 NAS에서 받아 설치해요. HIWARE로 두 번 올리지 않아도 돼요.
- **학습 데이터는 각 서버의 `/app`(로컬 SSD)에 둬요.** 이미지처럼 작은 파일이 많으면 NAS는 파일을 여는 데 시간이 걸려요. NAS는 옮기기와 보관용으로 써요. `/app` 속도를 재면 비교할 수 있어요.
- `scp` 하나로는 이더넷 카드 하나(10 Gbps, 1.2 GB/s 안팎)까지만 나와요. 암호화 때문에 그보다 낮을 수도 있어요.

**더 잴 것:** 아래 "한 번에 재기"를 두 서버에서 실행하면 나머지(서버 2 정보, 로컬 SSD, NAS 8줄기, IPoIB, 같은 InfiniBand 망인지, RDMA)를 모두 재요.

## 도커 관리

```bash
# [B200 서버] root
systemctl status b200-docker            # 상태
systemctl restart b200-docker           # 다시 켜기(돌던 컨테이너는 멈춰요)
journalctl -u b200-docker -n 50         # 기록
b200 who                                # GPU별 쓰는 사람
runuser -u shareduser -- env DOCKER_HOST=unix:///run/user/$(id -u shareduser)/docker.sock /opt/b200/docker/current/docker ps -a
```

- 설정 파일: `/etc/b200/docker/daemon.json` (root 만 고쳐요). 저장 위치: `/app/docker`.
- 기본 런타임은 runc 예요. nvidia 를 기본으로 하면 `--gpus` 없이 띄운 CUDA 이미지에도 GPU 8장이 모두 보여서 바꾸지 않아요.
- 오래된 이미지는 알림만 가요. 지워야 하면 들여온 사람에게 먼저 말하고, 위 `runuser` 줄의 `ps -a` 를 `rmi <이미지>` 로 바꿔 지워요.
- 도커 판 올리기: 접근 PC에서 `docker_pack.ps1` 을 다시 실행해 새 묶음을 올리고 `docker_install.sh` 를 다시 실행해요. 예전 판은 `/opt/b200/docker/<판>` 에 남아 있어 되돌리기 쉬워요.

## 드라이버 업데이트

`admin_setup.sh` 가 NVIDIA 패키지를 고정(`apt-mark hold`)해 두었어요. 업데이트는 팀에 미리 알리고 GPU가 비었을 때 해요.

```bash
# [B200 서버] root
apt-mark unhold $(apt-mark showhold | grep -E 'nvidia|cuda|nvlsm')
# ... 서버 관리 팀과 드라이버·Fabric Manager 를 같은 판으로 업데이트 ...
bash /app/inbox/admin_setup.sh          # 다시 고정
b200 doctor                             # 확인
```

## 되돌리기

```bash
# [B200 서버] root
bash /app/inbox/admin_setup.sh --undo   # 접속 설정·정기 점검 지우기, 공용 폴더 잠금 풀기
systemctl disable --now b200-docker     # 도커 끄기
```
