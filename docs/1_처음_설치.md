# 처음 설치하기

새로 설치한 GPU 서버를 이 문서 순서대로 준비하면, 팀원이 바로 접속해 도커로 학습을 돌릴 수 있는 상태가 돼요. 서버 2대 모두 같은 순서로 하되, 4·5단계(데이터셋·모델)는 두 서버 중 한 곳에서 한 번만 해요.

순서는 크게 셋이에요.

1. **준비(1단계)**: root 가 안전하게 설치할 자리를 만들어요.
2. **설치(2~5단계)**: 기초 프로그램, 도커, 데이터셋, 모델을 넣어요.
3. **권한·규칙 설정과 알리기(6·7단계)**: 팀원 맞이 설정(이름 고르기, 도우미, 알림)을 걸고 팀원에게 규칙을 알려요. 권한 설정은 서버 관리 팀 설정에 따라 마음대로 안 될 수 있어요. 그래서 맨 끝에 두고, 하나가 안 돼도 멈추지 않고 알려만 준 뒤 나머지를 계속해요. 안 되는 게 있어도 서버는 쓸 수 있어요.

- 서버는 지금 RHEL 9이고, 서버 관리 팀이 **Ubuntu 24.04 LTS** 로 다시 설치해요(2026-11-12 완료 예정). 이 문서는 Ubuntu로 다시 설치한 뒤의 순서예요. 서버로 가져가는 묶음도 Ubuntu 24.04 에 맞춰 만들어요.
- 접근 PC(인터넷이 되는 윈도우 PC)에서 할 일(묶음·데이터셋·모델 받기)은 서버 설치를 기다리지 않고 미리 해 둘 수 있어요.
- 설치하면서 무엇이 생기고 왜 그렇게 했는지는 `docs/3_구조와_보안.md` 에 있어요.

## 전체 흐름

| 단계 | 접근 PC (PowerShell, `D:\gpu`) | 올릴 것 → `/app/upload` (공용 계정 FileZilla) | GPU 서버 (root, `/app/inbox` 로 복사·지문 확인한 뒤) | 끝나면 확인할 것 |
|---|---|---|---|---|
| 0. 점검 | `.\pc\check.ps1` (접근 PC. 결과는 `reports\` 로 git 에) | `server\check.sh` → NAS 의 `/data/autonomy_sw/inbox` 에 한 번(서버는 아무것도 고치지 않아요) | 두 서버에서 각각 `GPU_ACCOUNT=<계정> bash /data/autonomy_sw/inbox/check.sh`. 보고서는 공용 계정 홈에 | `[문제]` 가 없어요 |
| 1. 준비 | `.\pc\setup_pack.ps1` | `setup\gpu-setup.tar` | `cd /app/inbox && tar xf gpu-setup.tar && bash prepare.sh` | `/app` 이 root 소유로 잠기고 `gpu fetch` 가 생겨요 |
| 2. 서버 기초 프로그램 | `.\pc\pkgs_pack.ps1` | `pack_pkgs\gpu-pkgs.tar` | `cd /app/inbox && tar xf gpu-pkgs.tar && bash pkgs_install.sh` | "기초 프로그램 …개가 모두 있어요" |
| 3. 도커 | `.\pc\docker_pack.ps1` | `pack_docker\gpu-docker.tar` | `cd /app/inbox && tar xf gpu-docker.tar && bash docker_install.sh` | "rootless로 동작해요" |
| 4. 데이터셋 풀기 | `.\pc\datasets_download.ps1` | `datasets` 폴더 | `bash /app/inbox/datasets/datasets_unpack.sh` | 데이터셋마다 라벨 수가 보여요 |
| 5. 사전학습 모델 넣기 | `.\pc\models_download.ps1` | `models` 폴더 | `bash /app/inbox/models/models_place.sh` | 모델마다 크기·라이선스가 보여요 |
| 6. 권한·규칙 설정 | (1단계 묶음에 들어 있어요) | | `cd /app/inbox && bash admin_setup.sh` | "완료". `[주의]` 가 있으면 서버 관리 팀과 정리 |
| 7. 팀원에게 알리고 확인 | | | 공용 계정으로 접속 | 이름 목록, "GPU별 사용자" 표, GPU 계산 |

- 접근 PC 명령 앞에는 모두 `powershell -ExecutionPolicy Bypass -File` 이 붙어요.
- 공용 계정은 팀원 모두가 같이 쓰는 서버 계정 하나예요. 지문은 파일 내용으로 계산한 sha256 값으로, 올린 파일이 바뀌지 않았는지 맞춰 볼 때 써요.
- 올린 파일을 root 가 들여오는 방법은 아래 "모든 단계에 공통" 의 "서버에 파일 올리기" 에 있어요. 단계마다 같은 방법이에요.
- 모든 명령은 여러 번 다시 실행해도 돼요. 끝난 것은 건너뛰고, 받다 만 것은 이어서 받아요.

## 시작하기 전에

### 서버 관리 팀에 요청할 것

| 항목 | 요청 내용 | 이유 |
|---|---|---|
| Ubuntu 버전 | 24.04 LTS(확정) | 설치 스크립트와 도커 묶음이 Ubuntu 24.04 기준이에요 |
| NVIDIA 드라이버 | 580 이상, open 커널 모듈(예: `nvidia-driver-580-open`). 지금은 595 예요 | 최신 CUDA(13.0)로 만든 팀원 이미지도 돌아가요. H200은 두 커널 모듈 모두 되지만 NVIDIA가 open 을 권장해요 |
| Fabric Manager | **필요 없어요.** 설치돼 있어도 꺼 두기 | 우리 GPU는 H200 NVL(PCIe 카드)이라 NVSwitch가 없고, NVLink는 브리지로 이어져요. HGX(SXM) 보드로 바뀌면 드라이버와 같은 버전으로 설치해야 해요(없으면 오류 802) |
| Persistence mode | `nvidia-persistenced` 켜기 | 켜 두면 GPU를 처음 쓸 때 몇 초씩 기다리지 않아도 돼요 |
| NAS | 두 서버 모두 `/data` 에 연결된 그대로 두기, root squash(NAS가 서버의 root 를 일반 사용자로 바꿔 다루는 설정)는 켜지 않기 | 데이터셋·모델을 NAS의 `/data/autonomy_sw` 에 root 소유로 한 번만 설치하고 두 서버가 같이 읽어요(`docs/8_NAS.md`) |
| `/app` | 2 TB SSD를 `/app` 에 연결하기(주인은 root 그대로). **가능하면 `/app` 은 포맷하지 않기** | 팀원 작업 폴더와 도커 이미지가 있어요(데이터셋·모델은 NAS에 있어서 포맷해도 남아요). 공용 계정 쓰기 권한은 필요 없어요. 1단계 `prepare.sh` 가 `/app/autonomy_sw` 의 쓰기 권한만 공용 계정에 줘요 |
| 서버 2 같이 쓰기 | 다른 팀이 서버 2에 어떤 계정으로 들어오는지, `/app` 을 같이 쓰는지 | 우리 팀은 서버 2의 GPU 4~7번만 써요. 다른 팀이 `/app` 에 폴더를 두고 있으면 1단계 `prepare.sh` 가 잠그기 전에 물어봐요 |
| 계정 | 팀원이 같이 쓰는 계정 하나, 이전과 같은 이름. sudo·docker 그룹은 넣지 않기 | 0단계에서 이 이름을 서버의 `/etc/gpu/account` 에 한 번 적으면 모든 스크립트가 거기서 읽어요 |
| 서버 프로그램 | 요청하지 않아요. 아래 "서버 기초 프로그램" 은 관리자가 2단계에서 직접 설치해요 | 서버에 인터넷이 없어서 접근 PC에서 `.deb` 파일을 받아 가요. OS 설치 때 서버 관리 팀이 함께 넣어 주면 2단계는 이미 있는 것을 건너뛰어 금방 끝나요. 학습에 쓰는 도구(Python 패키지, CUDA 등)는 팀원이 도커 이미지에 넣어 와서 서버에는 필요 없어요 |
| InfiniBand 도구 | InfiniBand 드라이버 묶음 DOCA-OFED 를 설치할 때 `perftest`, `infiniband-diags`, `ibverbs-utils` 도 함께(DOCA-OFED 에 들어 있어요) | 두 서버를 묶어 학습할 때 쓰는 RDMA 속도와 InfiniBand 망을 확인해요. 이더넷·IPoIB·NAS 속도는 이미 쟀어요(`docs/4_네트워크.md`). DOCA-OFED 가 없으면 2단계에서 Ubuntu 것을 설치하고, 있으면 2단계가 건너뛰어요(둘을 섞으면 충돌할 수 있어요) |

#### 서버 기초 프로그램

관리자와 팀원이 서버 화면(컨테이너 밖)에서 쓰는 프로그램과 설치 스크립트가 쓰는 프로그램이에요. 서버에 인터넷이 없어서 관리자가 2단계에서 묶음(`gpu-pkgs.tar`)으로 직접 설치해요. 목록은 아래 명령과 같아요(인터넷이 되는 Ubuntu 라면 이 명령 그대로 설치돼요). 빠진 것이 있으면 `check.sh` 가 "관리자가 직접 할 것" 에 패키지 이름을 적어 줘요.

```bash
apt install -y \
  tmux screen vim nano micro less htop btop nvtop iotop sysstat lsof strace tree ncdu jq bc file \
  rsync zip unzip p7zip-full pigz zstd xz-utils pv \
  git git-lfs curl wget python3 perl gawk \
  iperf3 ethtool perftest infiniband-diags ibverbs-utils
```

| 묶음 | 쓰는 곳 |
|---|---|
| `tmux screen` | 접속이 끊겨도 명령이 계속 돌게 해요(긴 설치, 학습 실행) |
| `vim nano micro less` | 서버 화면에서 파일 보기·고치기 |
| `htop btop nvtop iotop sysstat lsof strace` | CPU·GPU·디스크 사용량과 멈춘 프로세스 보기 |
| `tree ncdu jq bc file` | 폴더 구조·크기 보기, JSON 읽기 |
| `rsync zip unzip p7zip-full pigz zstd xz-utils pv` | NAS로 옮기기, 압축 풀기(데이터셋 설치에 `unzip` 이 꼭 필요해요), 진행률 보기 |
| `git git-lfs curl wget python3 perl gawk` | 코드 받기, 설치 스크립트가 쓰는 명령 |
| `iperf3 ethtool perftest infiniband-diags ibverbs-utils` | 네트워크·InfiniBand 점검(`check.sh`) |

서버 관리 팀에 요청할 것은 위 표뿐이에요. 나머지(준비, 기초 프로그램, 도커, 데이터셋, 모델, 권한·규칙 설정)는 관리자 root 계정으로 해요. HIWARE(서버에 접속할 때 거치는 사내 접속 관리 시스템)에서 root 는 PuTTY만 되고 FileZilla는 안 돼요. 파일은 공용 계정의 FileZilla로 올려요.


### 포맷하기 전에

- `/app` 을 포맷하는지 서버 관리 팀에 확인하세요.
- `/app` 도 포맷한다면 팀원들이 `/app/autonomy_sw` 의 실험 결과를 NAS에 옮겨 두게 하세요.
- 데이터셋·모델은 NAS(`/data/autonomy_sw`)에 있어서 `/app` 을 포맷해도 남아요. 예전처럼 `/app` 에 설치해 둔 것이 있으면 포맷하기 전에 NAS로 옮겨 두세요(`docs/8_NAS.md` 의 "처음 만들기").
- 접근 PC의 `D:\gpu\datasets`, `D:\gpu\models` 폴더는 지우지 마세요. 지워져도 이 폴더를 그대로 다시 올리면 돼요.


### 접근 PC 준비

1. 접근 PC에 git, uv 가 설치돼 있어야 해요.
2. 시작 메뉴에서 **PowerShell** 을 여세요(관리자 권한 필요 없음, PowerShell ISE 아님).
3. 저장소를 받으세요. 공개 저장소라 로그인 없이 받을 수 있어요. 이미 받았다면 `cd D:\gpu` 후 `git pull` 만 하면 돼요.

```powershell
# [접근 PC] PowerShell
cd D:\
git clone https://github.com/Leejunhee17/my-remote.git gpu
cd D:\gpu
```

받는 데 몇 시간 걸릴 수 있어요. 노트북이면 전원을 연결하세요. 실행 중에는 스크립트가 절전 모드를 막아요.
받은 결과는 `D:\gpu` 의 `setup\`, `pack_pkgs\`, `pack_docker\`, `datasets\`, `models\` 에 생겨요(git에는 올라가지 않아요).

저장소를 받은 뒤 커밋 검사를 한 번 켜세요. 사내 정보나 토큰이 실수로 올라가지 않게 막아 줘요(`docs/4_네트워크.md` 의 "결과 가져오기" 의 "처음 한 번").

### 접근 PC 설정(.env)

토큰·프록시·WildScenes 링크 목록 경로처럼 실행할 때마다 입력하던 값은 저장소 맨 위의 `.env` 파일 하나에 적어 둬요.
모든 접근 PC 스크립트가 시작할 때 이 파일을 읽어서, 적어 둔 값은 다시 묻지 않아요. 공개 저장소라도 `.env` 는 git에 올라가지 않아요(`.gitignore` 와 커밋 검사가 막아요).

```powershell
# [접근 PC] PowerShell
cd D:\gpu
copy .env.example .env
notepad .env
```

| 이름 | 적는 것 | 비우면 |
|---|---|---|
| `GPU_RUN` | `pc\run_all.ps1` 이 차례로 할 작업(`setup,pkgs,docker,datasets,models`) | 다섯 가지 모두 |
| `HTTPS_PROXY` | 회사 프록시 주소(스크립트가 스스로 못 찾을 때만) | 윈도우 설정에서 스스로 찾아요 |
| `HF_TOKEN` | Hugging Face Read 토큰(`docs/6_모델.md` 의 "승인이 필요한 모델(gated) 받기") | 실행 중에 물어봐요 |
| `WILDSCENES_LINKS` | 포털에서 받은 WildScenes 링크 목록 `.txt` 의 경로(`docs/5_데이터셋.md` 의 "WildScenes 링크 목록으로 받기") | WildScenes 는 건너뛰어요 |

- 화면과 기록 파일에는 읽은 **이름만** 나오고 값은 나오지 않아요(`.env 에서 읽은 설정: HF_TOKEN, …`).
- PowerShell 창에서 `$env:HF_TOKEN = "…"` 처럼 먼저 정한 값이 있으면 그 값을 우선해요.

### 접근 PC 점검

받기 전에, 또는 받다가 막혔을 때 접근 PC를 한 번에 점검해요(아래 "0단계: 서버 점검" 과 짝이에요). **데이터셋·모델은 받지 않고 아무것도 고치지 않아요.** 사이트마다 앞부분(1 KB)만 요청하고, 받기 도구(aria2c)로 작은 파일 몇 개만 임시 폴더에 받아 본 뒤 지워요.

```powershell
# [접근 PC] PowerShell
cd D:\gpu
powershell -ExecutionPolicy Bypass -File .\pc\check.ps1            # 점검하고, 물어본 뒤 결과를 git 으로 올려요
powershell -ExecutionPolicy Bypass -File .\pc\check.ps1 -NoPush    # 결과 파일만 만들어요
```

| 보는 것 | 내용 |
|---|---|
| 윈도우·프로그램 | 윈도우·PowerShell 버전, 긴 경로 설정, `tar.exe`, git, uv, aria2c(`tools\aria2`) |
| 저장소 | 커밋 검사(`core.hooksPath`), 가릴 낱말 목록, git 사용자 이름, 커밋하지 않은 파일, git 으로 GitHub 접속, 저장소가 최신인지 |
| `.env` | 값을 적은 이름(값은 적지 않아요), 오타 같은 이름, `GPU_RUN`, `HF_TOKEN` 모양, WildScenes 링크 목록 파일이 있는지와 언제 만료되는지, 안 쓰는 예전 WildScenes S3 설정 |
| 프록시 | `.env` 의 프록시, 윈도우 프록시, 자동 프록시 설정(PAC) |
| 인터넷 | 받기 스크립트 다섯 개가 쓰는 사이트 전부(PyPI, GitHub, Ubuntu·Docker·NVIDIA 저장소, Hugging Face, 데이터셋 사이트, Google Drive, ModelScope, CSIRO). 받기 스크립트와 같은 .NET 방식으로(브라우저처럼 시스템 프록시와 윈도우 로그인을 써서) 첫 화면뿐 아니라 실제 파일 앞부분까지 요청해요. `HF_TOKEN` 으로 로그인되는지, WildScenes 링크가 받아지는지도 봐요 |
| 받기 도구 | aria2c 를 준비하고(없으면 받아요), 작은 파일(Ubuntu 목록, Hugging Face 파일, GitHub 배포 파일, 작으면 WildScenes 파일 하나)을 실제로 받아 봐요. 받기 스크립트는 모두 aria2c 로 받아요 |
| 시계 | PC 시계가 맞는지(5분 넘게 틀리면 WildScenes 서명과 인증서 확인이 실패해요) |
| 디스크 | 저장소 드라이브의 형식(FAT32 면 4 GB 넘는 파일이 안 돼요)과 남은 공간, 다른 드라이브의 남은 공간 |
| 받은 것 | 묶음 세 개(`setup`, `pack_pkgs`, `pack_docker`), 다 받은 데이터셋·모델, 받기마다 마지막 실행이 끝났는지와 멈춘 이유·`[문제]` 줄 |

- 끝에 "고칠 것" 이 모여요. 없으면 "모두 정상이에요" 가 나와요.
- 결과는 `reports\pc_check_공유용_<날짜>.txt` 예요. 계정·PC 이름, 프록시 주소, 사내 IP, 토큰·키·서명은 가려서 적어요. 물어본 뒤 그 파일 하나만 커밋해 올려요(커밋 검사가 한 번 더 봐요). 담당자는 그 파일을 읽어요.
- WildScenes 링크만 자세히(머리글·aria2c 기록·이어받기까지) 보려면 `pc\wildscenes_check.ps1` 을 써요(`docs/5_데이터셋.md` 의 "WildScenes 링크 목록으로 받기").

### 한 번에 받기

`.env` 를 채웠다면 1~5단계의 접근 PC 일을 명령 하나로 이어서 할 수 있어요. 하나가 멈춰도 나머지는 계속하고, 끝에 결과를 한눈에 보여 줘요. 끝난 것은 건너뛰니 몇 번이고 다시 실행해도 돼요.

```powershell
# [접근 PC] PowerShell
cd D:\gpu
powershell -ExecutionPolicy Bypass -File .\pc\run_all.ps1                       # .env 의 GPU_RUN 대로
powershell -ExecutionPolicy Bypass -File .\pc\run_all.ps1 -Run models,datasets   # 이번에만 고른 것
```

서버에 올리고 설치하는 일은 이 명령이 하지 않아요. 각 작업이 끝날 때 보여 주는 안내(지문 포함)와 아래 단계를 따라 하세요. 지문은 `D:\gpu\지문_기록.txt` 에도 모여요.


## 모든 단계에 공통

1단계부터 5단계까지는 모두 "접근 PC에서 만들기 → 올리기 → root 가 복사해 지문 확인 → 실행" 순서예요. 올리는 방법과 실행 화면을 읽는 방법은 단계마다 같아서 여기 한 번만 적어요.

### 서버에 파일 올리기

root 는 FileZilla를 쓸 수 없어서, 설치 파일은 세 단계로 들여와요.

1. **공용 계정의 FileZilla로 `/app/upload` 에 올려요.**
2. **root 로 `/app/inbox` 에 새로 복사해요.**
3. **복사본의 지문(sha256)이 접근 PC 화면의 지문과 같은지 보고 나서 실행해요.**

`/app/upload` 는 공용 계정 폴더라 팀원 누구든 파일을 바꿀 수 있어요. root 가 실행하는 것은 root 만 고칠 수 있는 `/app/inbox` 의 복사본이에요. 지문이 같으면 접근 PC에서 만든 것과 한 글자도 다르지 않아요.

| 올리는 것 | 접근 PC의 지문 | GPU 서버(root): 복사하고 지문 보기 |
|---|---|---|
| `gpu-setup.tar` | `setup_pack.ps1` 끝에 나와요 | 처음: `cp /app/upload/gpu-setup.tar /app/inbox/ && sha256sum /app/inbox/gpu-setup.tar`, 그 뒤: `/app/admin/bin/gpu fetch gpu-setup.tar` |
| `gpu-pkgs.tar` | `pkgs_pack.ps1` 끝에 나와요 | `/app/admin/bin/gpu fetch gpu-pkgs.tar` |
| `gpu-docker.tar` | `docker_pack.ps1` 끝에 나와요 | `/app/admin/bin/gpu fetch gpu-docker.tar` |
| `datasets` 폴더 | `datasets_download.ps1` 끝에 나와요 | `/app/admin/bin/gpu fetch datasets` |
| `models` 폴더 | `models_download.ps1` 끝에 나와요 | `/app/admin/bin/gpu fetch models` |

- 지문은 64글자예요. 접근 PC는 대문자, 서버는 소문자로 보여 줄 수 있어요. 대소문자와 상관없이 글자만 같으면 돼요. 앞뒤 8글자씩 맞춰 봐도 충분해요.
- 접근 PC 스크립트는 지문을 `D:\gpu\지문_기록.txt` 에도 날짜와 함께 쌓아 둬요. 업로드가 끝난 뒤나 다른 날 맞춰 볼 때 여기서 찾으세요.
- 끝 화면에 "GPU 서버가 쓰지 않는 큰 파일" 이 나오면(받다 만 파일, 목록에서 뺀 모델) 그 파일은 빼고 올려도 돼요.
- **지문이 다르면 실행하지 마세요.** `/app/upload` 의 파일을 지우고 다시 올려 새로 복사하세요.
- 1단계(`prepare.sh`)부터는 `/app/admin/bin/gpu fetch <이름>` 이 복사와 지문 보기를 한 번에 해요. 올린 폴더에 링크가 섞여 있으면 복사본을 지우고 멈춰요. 링크가 있으면 지문을 본 뒤에 누군가 링크가 가리키는 파일을 바꿔치기할 수 있기 때문이에요.
- 폴더(데이터셋·모델)는 `MANIFEST.sha256`(파일 목록과 체크섬)과 설치 스크립트를 이어 붙여 계산한 지문 하나만 확인해요. 나머지 파일은 설치 스크립트가 `MANIFEST.sha256` 으로 하나하나 확인하고, 목록에 없는 파일은 옮기지 않아요.
- 큰 파일 전송이 끊기면 다시 올릴 때 **이어받기**를 고르세요. 설치가 끝나면 `/app/upload` 의 원본을 지워 공간을 비우세요.

### 실행 화면 읽기

| 표시 | 뜻 | 할 일 |
|---|---|---|
| `[정상]` 초록 | 확인했어요 | 없어요 |
| `[주의]` 노랑 | 계속 진행하지만 알아 둘 내용이 있어요 | 메시지를 읽으세요 |
| `[문제]` 빨강 | 끝까지 진행하지만 고칠 것이 있어요 | 메시지에 적힌 할 일을 하세요 |
| `멈춤` 빨간 상자 | 더 진행할 수 없어요 | 상자 안의 **할 일** 을 한 뒤 **같은 명령을 다시 실행** 하세요 |

해결이 안 되면 `docs/7_문제_해결.md` 를 보세요.


## 0단계: 서버 점검

`server\check.sh` 하나로 서버·NAS·네트워크를 한 번에 점검하고 보고서도 하나로 남겨요.
**이 단계에서는 서버에서 아무것도 고치지 않아요.** 설정 파일을 쓰거나, 폴더를 만들거나, 주인·권한을 바꾸는 일은 점검 결과를 보고 고칠 것을 다 고친 뒤 1단계에서 해요.
서버에 남는 것은 공용 계정 홈의 보고서 두 개뿐이에요. 점검하면서 만드는 임시 폴더와 시험 파일(`/tmp`, NAS 의 `/data/tmp/.gpu_net`, 속도 시험 파일)은 끝나면 지워요.

**root 로 실행해요.** 1단계 전에는 NAS 의 `/data/tmp`(root 소유 755)에 root 만 쓸 수 있어서, root 여야 두 서버가 NAS로 서로를 찾고 NAS 속도를 잴 수 있어요. 다만 `/data` 자체를 root 말고도 고칠 수 있으면(2026-11-06 현재 이 상태예요) root 도 NAS에 쓰지 않고 그 부분을 건너뛰어요. `docs/8_NAS.md` 의 "이미 있는 팀 폴더 잠그기" 를 보세요.

1. 공용 계정의 FileZilla로 `server\check.sh` 를 NAS 의 **`/data/autonomy_sw/inbox`** 에 한 번만 올려요. 두 서버가 같은 NAS 를 보니까 서버마다 올릴 필요가 없어요.
2. 두 서버에서 각각 root 로 실행해요. 두 번째 서버는 첫 번째 서버에서 실행한 뒤 10분 안에만 실행하면 돼요.
3. 두 서버 모두 끝나면 올린 `check.sh` 는 FileZilla로 지워요.

```bash
# [GPU 서버] root, 두 서버에서 각각. <계정이름> 을 실제 공용 계정 이름으로 바꿔요(< > 도 지워요)
GPU_ACCOUNT=<계정이름> bash /data/autonomy_sw/inbox/check.sh
```

| 보는 것 | 내용 |
|---|---|
| 서버 | 운영체제, 공용 계정, 드라이버, GPU 8장, NVLink(PCIe 카드면 브리지로 묶인 GPU, HGX 보드면 Fabric), `/app` 주인과 SSD 여부, 서버에 설치돼 있어야 할 프로그램(위 "서버 기초 프로그램") |
| 서버 폴더·권한 | `/app` 과 그 아래 두 단계, `/home`, 설치 스크립트가 쓸 시스템 폴더(`/etc/profile.d`, `/etc/cron.d`, `/usr/local/bin`, `/opt` 등)의 주인·그룹·권한과 링크. `/app` 아래 root·공용 계정이 아닌 계정의 것, 링크, 누구나 쓰는 폴더, root 말고도 고칠 수 있는 시스템 폴더, 공용 계정의 관리자 그룹·sudo 를 알려 줘요 |
| 네트워크 | 카드 종류·속도·주소, InfiniBand 포트 |
| NAS | 연결 방식·옵션, 용량, 최상위 폴더의 주인·권한, 계정 번호, 팀 폴더(`/data/autonomy_sw`), 공용 계정이 쓸 수 있는 곳, root squash |
| 속도 | NAS로 상대 서버를 찾아 서버 사이(이더넷·IPoIB·RDMA), 로컬 SSD(root 소유 `/app` 이면), NAS 속도를 재요(`docs/4_네트워크.md` 의 "전체 점검"). 두 서버의 공용 계정 번호가 같은지도 여기서 맞춰 봐요 |

- **정상이면** 마지막에 "모두 정상" 이 나와요.
- **`[문제]` 가 있으면** 화면 끝의 "서버 관리 팀에 요청할 것" 목록을 그대로 보내고, "관리자가 직접 할 것" 은 직접 하세요.
- 보고서는 공용 계정 홈에 원본(`check_report_…txt`)과 공유용(`check_공유용_…txt`) 두 개로 생겨요. root 가 아니라 공용 계정 권한으로 만들어서 파일 주인도 공용 계정이에요(홈에 누가 링크를 심어 둬도 root 가 다른 파일을 덮지 않아요). 공유용만 FileZilla로 내려받아 git 으로 올려요(`docs/4_네트워크.md` 의 "결과 가져오기").
- 상태만 빨리 보려면 앞에 `QUICK=1` 을 붙여요(`QUICK=1 GPU_ACCOUNT=<계정이름> bash /data/autonomy_sw/inbox/check.sh`). 속도를 재지 않아서 1분 안에 끝나요.
- 1단계 뒤에 다시 점검할 때는 묶음에 든 것을 그대로 써요: `bash /app/inbox/check.sh`(공용 계정 이름은 `/etc/gpu/account` 에서 읽어요).
- 상대 서버를 기다리고 속도를 재느라 몇 분에서 15분쯤 걸려요. `tmux` 안에서 실행하면 HIWARE 접속이 끊겨도 계속 돌아요(`tmux` → 명령 → 끊기면 다시 접속해 `tmux attach`). 서버에 tmux 가 아직 없으면 그냥 실행하세요. 끊기면 같은 명령을 다시 실행하면 돼요.
- 공용 계정으로도 실행할 수 있어요. 다만 1단계 전에는 공용 계정이 쓸 수 있는 NAS 폴더가 없어서 상대 서버 찾기와 NAS 속도는 건너뛰어요(1단계 뒤에는 `/data/autonomy_sw/tmp_transfer` 를 써요).
- 네트워크 결과를 읽는 방법은 `docs/4_네트워크.md`, NAS 결과로 정할 것은 `docs/8_NAS.md` 에 있어요.


## 1단계: 준비

root 가 설치 스크립트를 안전하게 돌릴 자리를 만들어요. 팀원에게 보이는 설정은 아직 하지 않아요.

접근 PC에서 묶음을 새로 만드세요. 묶음에는 서버 스크립트(준비 `prepare.sh`, 6단계 권한·규칙 설정 `admin_setup.sh`, 점검 스크립트, 도우미)만 들어 있어서 몇 초면 끝나요.

```powershell
# [접근 PC] PowerShell
cd D:\gpu
git pull
powershell -ExecutionPolicy Bypass -File .\pc\setup_pack.ps1
```

### 처음 한 번: 공용 계정 이름과 올릴 폴더

서버를 고치는 첫 일이에요. 0단계 점검에서 `[문제]` 를 다 고친 뒤 root 로 한 번 해요. 공용 계정 이름을 서버에 적고, 설치 파일을 올릴 `/app/upload` 와 root 가 지문을 확인한 복사본을 두는 `/app/inbox` 를 만들어요(그다음부터는 `prepare.sh` 가 이 폴더들을 맞춰요).
`/app` 을 포맷하지 않아 예전 파일이 남아 있으면 누군가 링크를 심어 뒀을 수 있으니, 먼저 확인한 뒤 만들어요.

```bash
# [GPU 서버] root, 처음 한 번
mkdir -p /etc/gpu && echo <계정이름> > /etc/gpu/account   # <계정이름> 을 실제 공용 계정 이름으로 바꿔요(< > 도 지워요)
chmod 644 /etc/gpu/account && id "$(cat /etc/gpu/account)"   # uid=... 가 나오면 맞게 적은 거예요
ls -ld /app /app/inbox /app/upload                   # /app·inbox 주인이 root 가 아니거나 inbox·upload 가 링크(->)면 멈추고 아래를 보세요
mkdir -p /app/inbox /app/upload && chown -h root:root /app/inbox && chmod 755 /app/inbox && chown -h "$(cat /etc/gpu/account):" /app/upload
```

- `/app` 주인이 root 가 아니면 공용 계정이 그 사이에 링크를 바꿔 넣을 수 있어요. 다른 계정 폴더가 없으면 `chown root:root /app && chmod 755 /app` 으로 먼저 잠그세요. 서버 2처럼 다른 팀 폴더가 있으면 그 팀과 협의한 뒤에 하세요.
- `inbox` 나 `upload` 가 링크면 `rm /app/inbox`(링크만 지워요)로 지운 뒤 다시 하세요.
- `id` 줄에서 `no such user` 가 나오면 계정 이름을 잘못 적은 거예요. 첫 줄을 고쳐 다시 하세요.

### 준비 실행

`setup\gpu-setup.tar` 를 `/app/upload` 에 올리세요. root 로 복사해 지문을 확인한 뒤, 묶음 안의 `prepare.sh` 를 실행하세요.

```bash
# [GPU 서버] root, 두 서버에서 각각
cp /app/upload/gpu-setup.tar /app/inbox/ && sha256sum /app/inbox/gpu-setup.tar   # 접근 PC 화면의 지문과 같은지
cd /app/inbox && tar xf gpu-setup.tar && bash prepare.sh
```

`prepare.sh` 가 하는 일이에요.

- `/app` 을 root 소유로 잠가요. 다른 팀이 `/app` 에 폴더를 두고 있으면 잠그기 전에 물어봐요.
- `/app/admin`(도우미·설정)과 `/app/inbox`(root 가 설치 파일을 두는 곳)를 root 만 고칠 수 있게 만들어요. `/app/upload`(올리는 곳)와 `/app/autonomy_sw`(팀원 작업 공간)는 공용 계정 폴더로 만들어요.
- 알림 기준과 NAS 위치를 적은 `/app/admin/gpu.conf` 를 만들어요.
- NAS 팀 폴더(`/data/autonomy_sw`)와 그 안의 `datasets`·`models`(root 만 고쳐요), `backup`·`docker_images`·`tmp_transfer`(팀원이 써요)를 만들어요. NAS가 root squash 라 만들지 못하면 알려만 줘요. 그때는 4·5단계를 할 수 없으니 서버 관리 팀에 요청하세요(`docs/8_NAS.md`).
- 올린 파일을 `/app/inbox` 로 옮기고 지문을 보여 주는 `gpu fetch` 명령(`/app/admin/bin/gpu`)을 설치해요.
- 예전 방식의 `/app/shared` 가 있으면 명단·배분·알림 설정만 `/app/admin` 으로 옮기고, 나머지(예전 기초 프로그램, 데이터셋·모델)는 `/app/.shared_old_<날짜>` 로 치워요. 공용 계정이 바꿔 뒀을 수 있는 프로그램을 root 가 실행하지 않게 하려는 거예요. 예전 데이터셋·모델을 NAS로 옮기는 `rsync` 명령은 화면에 나와요.

**준비가 설치보다 먼저인 이유:** 설치 스크립트는 모두 root 로 돌아요. root 가 공용 계정이 고칠 수 있는 폴더에서 일하면, 팀원 누구든 미리 심어 둔 링크를 따라 root 가 시스템 파일을 덮어쓰거나 바꿔 둔 프로그램을 실행하게 돼요. 그래서 2~5단계 스크립트는 `/app` 과 `/app/inbox` 가 잠겼는지 확인하고, 잠겨 있지 않으면 멈춰요.

## 2단계: 서버 기초 프로그램

서버 화면에서 쓰는 tmux, nvtop, rsync 같은 프로그램(위 "서버 기초 프로그램")을 설치해요. 서버에 인터넷이 없어서, 접근 PC가 Ubuntu 24.04 저장소에서 `.deb` 파일을 **의존 패키지까지 모두** 받아 묶어요(약 160개, 70 MB 안팎).

```powershell
# [접근 PC] PowerShell
cd D:\gpu
powershell -ExecutionPolicy Bypass -File .\pc\pkgs_pack.ps1
```

`pack_pkgs\gpu-pkgs.tar` 를 `/app/upload` 에 올리고, root 로 복사해 지문을 확인한 뒤 설치하세요. 1단계 준비(`prepare.sh`)를 먼저 해 둬야 해요.

```bash
# [GPU 서버] root, 두 서버에서 각각
/app/admin/bin/gpu fetch gpu-pkgs.tar        # 새로 복사하고 지문을 보여 줘요. 접근 PC 화면의 지문과 같은지
cd /app/inbox && tar xf gpu-pkgs.tar && bash pkgs_install.sh
```

`pkgs_install.sh` 가 하는 일이에요.

- 묶음 안 파일의 체크섬을 하나하나 확인하고, 목록에 없는 파일이 섞여 있으면 멈춰요.
- 목록의 프로그램 중 **서버에 없는 것만** 골라요. 이미 있는 것은 그대로 둬요(버전도 올리지 않아요).
- 묶음의 `debs` 폴더로 임시 apt 저장소를 만들어 설치해요. 의존 순서는 apt 가 맞추고, 새 프로그램이 더 새 버전을 요구하는 기본 패키지만 올려요. 서버의 apt 설정과 목록(`/etc/apt`, `/var/lib/apt/lists`)은 건드리지 않아요.
- 설치하려면 다른 패키지를 지워야 하는 경우에는 아무것도 바꾸지 않고 멈춰요(다른 팀이 쓰는 것을 지우지 않게).
- InfiniBand 드라이버 묶음(DOCA-OFED)이 있으면 InfiniBand 도구 세 개는 건너뛰어요.

확인할 것이에요.

- 끝에 "기초 프로그램 …개가 모두 있어요" 가 나오면 돼요. 여러 번 실행해도 되고, 다 있으면 "설치할 것이 없어요" 로 끝나요.
- 묶음은 Ubuntu 24.04(noble) 용이에요. 서버 버전이 다르면 처음에 멈춰요.
- 목록을 바꾸려면 `pc\pkgs_pack.ps1` 의 `$Pkgs`, 위 "서버 기초 프로그램" 명령, `server\check.sh` 의 목록을 같이 고쳐요(`bash tests/run.sh docs` 가 셋이 같은지 봐요).


## 3단계: 도커

```powershell
# [접근 PC] PowerShell
cd D:\gpu
powershell -ExecutionPolicy Bypass -File .\pc\docker_pack.ps1
```

`pack_docker\gpu-docker.tar` 를 `/app/upload` 에 올리고, root 로 복사해 지문을 확인한 뒤 설치하세요.

```bash
# [GPU 서버] root, 두 서버에서 각각
/app/admin/bin/gpu fetch gpu-docker.tar      # 새로 복사하고 지문을 보여 줘요. 접근 PC 화면의 지문과 같은지
cd /app/inbox && tar xf gpu-docker.tar && bash docker_install.sh
```

도커 데몬은 root 가 아니라 공용 계정 권한으로 돌아요(rootless). 컨테이너 안에서 무엇을 해도 서버 root 권한은 얻지 못해요.


## 4단계: 데이터셋 풀기

- **두 서버 중 한 곳에서 한 번만 해요.** 4·5단계 스크립트는 서버가 아니라 두 서버가 같이 보는 NAS(`/data/autonomy_sw/datasets`·`/data/autonomy_sw/models`)에 넣어요. 그래서 어느 서버에서 하든 다른 서버에서도 바로 보여요.
- 이 문서는 서버 1에서 하는 것으로 적었어요. 서버 2에서 해도 결과는 같아요. 다만 아래 두 가지는 지켜 주세요.
  - `/app` 공간이 넉넉한 서버에서 하세요. `gpu fetch` 가 올린 폴더를 `/app/inbox` 로 한 번 더 복사해서, 그 서버의 `/app` 에 올린 것과 복사본이 함께 들어가야 해요. 서버 2는 다른 팀과 `/app` 을 같이 쓸 수 있어서 공간이 더 빠듯할 수 있어요.
  - 두 서버에서 동시에 하지 마세요. 같은 NAS 폴더에 함께 쓰면 꼬일 수 있어요. 한쪽이 끝난 뒤 다른 쪽에서 다시 실행하는 건 괜찮아요. 이미 넣은 것은 건너뛰어요.
- 이미 NAS에 들어 있으면 할 일이 없어요. 0단계 점검 화면에 "/data/autonomy_sw/datasets 에 설치돼 있어요" 가 나와요.
- 예전 `/app/shared` 에 넣어 둔 것이 있으면 1단계 `prepare.sh` 가 NAS로 옮기는 명령을 보여 줘요. 그 명령으로 옮기면 다시 올리지 않아도 돼요.
- 처음이면 접근 PC의 `datasets` 폴더를 `/app/upload` 에 통째로 올린 뒤 아래를 실행해요. 다 풀면 `/app/upload`·`/app/inbox` 의 복사본은 지워도 돼요.
- 접근 PC의 지문은 `D:\gpu\지문_기록.txt` 에 남아 있어요. 없으면 `datasets_download.ps1` 을 다시 실행하세요. 끝에 지문이 나와요(받은 것은 건너뛰어 금방 끝나요).

```bash
# [GPU 서버 1(또는 2)] root, 한 곳에서만
/app/admin/bin/gpu fetch datasets             # 접근 PC 화면의 지문과 같은지
bash /app/inbox/datasets/datasets_unpack.sh
```

`datasets_unpack.sh` 는 체크섬을 확인한 뒤 압축을 원래 들어 있던 폴더에 풀고(압축이 아닌 rosbag·보정 파일은 그대로 복사), 데이터셋마다 라벨 파일 수를 세어 보여 줘요. 받는 방법과 목록은 `docs/5_데이터셋.md` 에 있어요.

## 5단계: 사전학습 모델 넣기

4단계와 같은 방식으로, 두 서버 중 한 곳에서 한 번만 해요. 접근 PC의 `models` 폴더를 `/app/upload` 에 통째로 올린 뒤 실행해요.

```bash
# [GPU 서버 1(또는 2)] root, 한 곳에서만
/app/admin/bin/gpu fetch models               # 접근 PC 화면의 지문과 같은지
bash /app/inbox/models/models_place.sh
```

`models_place.sh` 는 체크섬을 확인한 뒤 모델을 `/data/autonomy_sw/models/<만든 곳>/<모델>` 에 복사하고, 가중치 파일을 실제로 열어 텐서가 들어 있는지 확인해요. 받는 방법과 목록은 `docs/6_모델.md` 에 있어요.

- **서버 2가 쓸 설치 묶음(`gpu-setup.tar`, `gpu-pkgs.tar`, `gpu-docker.tar`)은 NAS에 남겨 두세요.** 서버 2는 HIWARE로 다시 올리지 않고 NAS에서 가져와요. 명령은 `docs/8_NAS.md` 의 "쓰는 법" 에 있어요.

## 6단계: 권한·규칙 설정

설치를 다 끝낸 뒤, 팀원에게 서버를 열기 전에 실행해요. 1단계 묶음에 들어 있어서 따로 올릴 것은 없어요.

```bash
# [GPU 서버] root, 두 서버에서 각각
cd /app/inbox && bash admin_setup.sh
```

`admin_setup.sh` 가 하는 일이에요.

- 공용 계정에 관리자 권한(sudo, docker 그룹 등)이 없는지 확인만 해요. 있으면 `[주의]` 로 알려요.
- GPU 배분 파일(`/app/admin/gpu_alloc.txt`)이 없으면 서버 번호를 물어보고 만들어요. **1** = 우리 팀만 쓰는 서버, **2** = 다른 팀과 같이 쓰는 서버(0~3번 다른 팀). 서버 이름 끝이 `p2` 면 Enter 를 눌렀을 때의 기본값이 2예요. 잘못 고르면 다른 팀 GPU 경고가 빠져요. 꼭 확인하고 답하세요.
- 팀원 명단(`/app/admin/team.txt`)에 있는 사람마다 작업 폴더(`/app/autonomy_sw/<이름>`)와 NAS 의 `backup/<이름>`·`docker_images/<이름>` 을 만들어요.
- 접속할 때 이름을 고르게 하고, 이름별 캐시·명령 기록·tmux 를 나눠요(`/etc/profile.d/gpu.sh`).
- `docker`·`nvidia-smi` 도우미를 설치해요(이름표, GPU 겹침 경고, "GPU별 사용자" 표).
- GPU 서비스(`nvidia-persistenced`)를 켜요.
- 10분마다 GPU 사용 기록과 알림, 월요일 아침 주간 보고서를 걸어요(`/etc/cron.d/gpu`).

**하나가 안 돼도 멈추지 않아요.** 권한은 서버 관리 팀 설정에 따라 마음대로 안 될 수 있어요. 공용 계정에 sudo 가 있거나 NAS 잠금이 막혀도, `[주의]` 로 알린 뒤 나머지 설정은 계속해요. `[주의]` 가 나온 것은 그 줄의 안내대로 서버 관리 팀과 정리하세요. 그동안에도 서버는 쓸 수 있어요. 기술로 다 막을 수 없는 부분은 팀 규칙(`team/서버_사용_규칙.md`)으로 채워요.

끝나면 `/app/admin/team.txt` 에 팀원 `이름 그룹` 을 적고 한 번 더 실행하세요. 팀원마다 작업 폴더가 생겨요.

되돌리려면 `bash admin_setup.sh --undo` 를 실행해요. 접속 설정과 정기 점검만 지우고, 준비에서 만든 폴더·잠금·`gpu` 명령은 그대로 둬요.

## 7단계: 팀원에게 알리고 확인

먼저 공용 계정으로 접속해 세 가지를 확인하세요.

1. 이름 목록이 나오고, 번호를 고르면 `/app/autonomy_sw/<이름>` 으로 이동해요.
2. `nvidia-smi` 아래에 "GPU별 사용자" 표가 붙어요. 서버 2는 0~3번이 "다른 팀" 으로 보여요.
3. `gpu doctor <PyTorch 이미지>` 를 실행하면 "보이는 GPU 1장 / GPU 계산 정상" 이 나와요. 서버에는 아직 이미지가 없으니, 팀원 안내(`team/사용_안내.md`)의 1~3단계대로 PyTorch 이미지 하나를 올려 공용 계정으로 `docker load` 하세요(예: 내 PC에서 `docker pull nvcr.io/nvidia/pytorch:<최근 태그>` → `docker save`). 드라이버로 실제 GPU 계산까지 되는지는 여기서 처음 확인해요. 서버 2에서는 다른 팀 GPU를 피해 우리 GPU(4번)로 시험해요.

여기까지 되면 팀원에게 `team/` 폴더의 규칙(`서버_사용_규칙.md`, 팀원 공유용 엑셀 `서버_사용_규칙.xlsx`)과 사용법(`사용_안내.md`)을 알려 주세요.
